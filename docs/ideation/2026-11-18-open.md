# What should XitDB Ruby build next?

## Subject

What should XitDB Ruby build next? The scope is the entire gem. It provides pure Ruby, single-file transactional collections, with portable and Ruby profiles. The public API already has snapshots, history, revert, streams, and sorted ranges. [README](../../README.md#transactions-and-limits) · [Portable profile](../portable.md)

The latest GitHub release, `v0.2.0` at `0004826`, writes `rb04`. On November 18, PR #9 merged `rb05` into GitHub `main` at `d08e1d0`. The inspected checkout, `014cee5`, is the PR head. [Release](https://github.com/svyatov/xitdb-ruby/releases/tag/v0.2.0) · [PR #9](https://github.com/svyatov/xitdb-ruby/pull/9) · [Changelog](../../CHANGELOG.md)

The GitHub issue list and open pull request list were empty when checked. The rankings reflect repository evidence, expected value, and estimated scope. The metrics pilot can establish the needs of one workload. [Issues](https://github.com/svyatov/xitdb-ruby/issues) · [Pull requests](https://github.com/svyatov/xitdb-ruby/pulls)

Sizes are relative to this repository. S is a focused example or tool change. M adds a bounded workflow or storage operation. L changes a wider storage or compatibility contract.

## Ranked ideas

### 1. Explicit migration from `rb04` to `rb05`

Add a one-way migration from the `v0.2.0` Ruby profile to a separate `rb05` file. Open the source read-only. Preserve typed keys, collection kinds, insertion order, and opaque codec payloads without running codec loaders. Require an explicit latest-only choice if the first version cannot retain history. Exercise the migration in CI with a populated file created by the released gem.

- direct: "Export earlier files with their matching gem version before upgrading." [`CHANGELOG.md:5`](../../CHANGELOG.md#L5)
- direct: "This pre-1.0 format has no migration or backward reader." [`docs/ruby.md:6`](../../docs/ruby.md#L6)

**Why it matters.** A separate migration path gives `v0.2.0` users a tested upgrade and leaves the source available for rollback.

## Cut

| Idea | Reason |
| --- | --- |
| Prior-release upgrade fixture and CI rehearsal | Combined with the migration. A rejection-only test does not prove that a user can upgrade. |
| General compatibility gate for every historical profile | Cost over value. Start with the profile written by the latest release. |
| Permanent multi-version Ruby reader | Cost over value. Each supported wire format would add a read path and maintenance work. |
| Stand-alone format header inspector | Combined with database verification and migration preflight. |
| Opaque codec inventory | Combined with structural verification. Application-specific codec readiness needs separate evidence. |
| Versioned typed export and import format | Cost over value. A new interchange contract is much broader than the immediate release migration. |
| General sharing-preserving logical conversion | Cost over value for this round. Path-dependent transforms require distinct outcomes for some shared inputs. |
| Select arbitrary checkpoints for a portable archive | Cost over value. A last-N policy gives rollback coverage with a smaller contract. |
| Writable fork from a checkpoint | Explicit cross-file copying can already populate a writable file from a snapshot. A dedicated API needs a concrete consumer. |
| Space and layout breakdown for an actual file | Cost over value for the first maintenance change. Attribute shared bytes before promising a space estimate. |
| Compaction savings predictor | Duplicate of the broader space report. A staged compacted file measures actual savings. |
| Backup sidecar with a whole-file digest | Cost over value for an initial local restore drill. Add when backups need transport or custody checks. |
| Atomic replacement of a live replica | Cost over value. Existing handles and writer coordination make cutover a separate contract. |
| Persistent replica negotiation or network service | Cost over value. Existing IO primitives cover transport and the initial workflow can stay local. |
| Idempotent write receipt recipe | Lower expected value now. The commit-outcome contract exists and there is no evidence of a caller making unsafe retries. |
| Page-local typed-array insert and delete | Basis incomplete. The fallback is documented, but application cost on `rb05` has no measured baseline here. |
| Optimize nested bulk storage immediately | Basis incomplete. Archived nested measurements apply to `rb04` and use synthetic nesting. |
| Application-specific performance gate in isolation | Combined with the metrics-history pilot to derive operation mix and limits from a real workload. |
| Resume cursor for nonunique indexes | Combined at the example level. A public cursor would also need an identity and lifetime contract. |
| Rebuild and audit a derived sorted index | Combined with the duplicate-safe index example. |
| Derived index replay from snapshot deltas | Cost over value as an initial diff consumer. Correct replay needs application-specific index rules. |
| Generic process crash matrix | Already done for ordinary commit interruption. Maintenance cases belong with the feature they exercise. |
| Dedicated maintenance interruption matrix | Fold uncovered interruption cases into migration and backup tests. Maintenance already has directory-sync fault tests. |
| Cross-profile state-machine replay | Useful engineering work, with weaker evidence of a current coverage gap than the release migration rehearsal. |
| Prepared imports for writer contention | Basis incomplete. Writer serialization is documented, but a representative lock-hold measurement is missing. |
| History-wide verifier with disk-spilled visitation | Combine bounded visitation with the verifier. Defer history-wide coverage until the latest-root scope is defined. |
