# Confirmation protocol

The predeclared design requires a fresh balanced confirmation for noisy or contradictory results.
A preliminary integrated result flagged insertion of 1,000 application records in memory; the prototype comparison had passed that case.
The complete integrated matrix must finish before confirmation begins.

For every group that fails an acceptance limit:

1. Preserve the original full matrix, exact sources, summary, and failed decisions.
2. Run twelve fresh measured observations per native implementation, plus two excluded warmups, using the unchanged worker and alternating order.
3. Verify identical library sources, fixture hashes, correctness coverage, and stored sizes.
4. Pool every original and confirmation observation for both native implementations within that group, retaining both epochs and all operations.
5. Apply the unchanged acceptance limits to the pooled medians; passing results elsewhere cannot hide a failure.

Report the original failure and confirmation outcomes explicitly.
Do not discard unfavorable observations or select only favorable operations from the confirmation.
Core JSON and column comparisons retain their original balanced observations unless they are repeated separately.
If a pooled group still fails, diagnose and revise the implementation, then obtain fresh measurements for the revised sources.
Never combine different implementation versions into one acceptance decision.

This protocol is recorded before obtaining confirmation observations.
