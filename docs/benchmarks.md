# Memory and performance measurements

The stress command measures file databases inside an isolated Linux container with a hard memory budget.
The benchmark command measures fixed workloads without timing pass thresholds.
Both commands require Docker and the cached `ruby:4.0.9-slim` image.
They use `--pull=never` and `--network=none` and fail when the required capability is unavailable.
They install nothing.

The separate [native Ruby record comparison](native-profile-performance.md) measures construction, reads, updates, history growth, and compaction against a fixed baseline revision.
It runs directly on the host and includes portable and JSON controls.

## Run the workloads

1. Run `ruby script/stress.rb --limit-mib 256 --data-mib 768`.
2. Run `ruby script/benchmark.rb --output pkg/benchmark.json`.
3. Run `bundle exec ruby -Ilib:test test/stress/memory_test.rb` for the covering tests.

The covering stress test executes the same 768 MiB command and saves its report in `pkg/stress.json`.
It therefore supplies the command evidence without a second standalone stress run.
The stress suite is separate from `rake test`.
Set `XITDB_STRESS_REPORT=PATH` to validate a previously captured report and republish it without starting another full workload.
This explicit mode checks recorded measurements and the report publication path; it does not provide a fresh Linux execution result.

Docker sets the container's memory and combined memory-plus-swap limits to the requested budget.
The child verifies Linux cgroup v2 `memory.max` and `memory.swap.max` before creating data.
Swap must be zero.
The report records these actual limits, `memory.peak`, and `memory.events`.
The cgroup peak includes kernel charges and file cache, not only Ruby's resident memory.
The budget applies during fixture creation, operations, and verification.

With Docker's systemd cgroup driver, the harness sets `memory.high` to 75% of the hard limit through runc's systemd annotation.
For the 256 MiB workload, this starts reclamation at 192 MiB while retaining the 256 MiB maximum and zero swap.
This gives the kernel time to reclaim filesystem cache before the hard limit can trigger an OOM kill.
The child verifies the configured threshold and records `memory_high_bytes` in its report.
Docker's cgroupfs driver retains its hard-limit behavior and records `memory_high_bytes` as `"max"`.
See [the kernel's memory controller guide](https://docs.kernel.org/admin-guide/cgroup-v2.html#usage-guidelines)
and [runc's systemd properties](https://github.com/opencontainers/runc/blob/main/docs/systemd.md#auxiliary-properties).

Each command checks available scratch space before starting.
Datasets use one task-owned temporary directory.
Profiles run sequentially, and each destination closes and unlinks before the next maintenance operation.
The parent removes the directory on normal completion or failure.
If the child fails, the parent removes its own container and reports the failure.
It does not use a weaker memory limit or skip a workload.

## Stress workload

Each profile stores 8,192 deterministic sorted rows and a 768 MiB byte value.
The generator writes one reusable 64 KiB chunk and retains one digest.
Two histories share the byte value and sorted rows, with different revision scalars.
`dataset_bytes` comes from the committed source file's actual size.
`payload_bytes` records the complete generated byte count.

Lookup checks present and absent keys.
Pagination checks every sorted row through pages of at most 37 entries.
Streaming checks the complete byte count and SHA-256 digest through public `open_bytes`.
Conversion copies both histories to the other profile.
Compaction retains the latest history in the original profile.
Both outputs receive lookup, pagination, history, revision, byte-count, and digest checks.
Verification times are separate from conversion and compaction times.
Destination file sizes record the output cost of each operation.

Converted Ruby Strings can use tagged envelopes that public `open_bytes` does not accept.
Their verification uses the existing profile byte descriptor and bounded range reads.
Original explicit byte streams use public `open_bytes` in both profiles.
Source reads exceeding 64 KiB fail throughout measured operations and destination verification.
The workload never decodes the large scalar or materializes a database root.

The offset-cache observer reads `OffsetMap#peak_cache_size` when each map closes.
It retains one maximum integer, without retaining maps, entries, or per-access records.
The covering test requires a positive observed peak no greater than 16,384 entries.

## Benchmark fields and interpretation

Each benchmark workload uses a 1 MiB payload, 256 sorted rows, and two histories.
Portable and Ruby profiles run against file and memory sources.
Every operation has three elapsed samples and three allocation counts.
The output records minimum, median, and maximum elapsed seconds, Ruby version, source sizes, destination sizes, and fixture times.
Allocation counts use `GC.stat(:total_allocated_objects)` differences.
They count Ruby objects, not bytes or retained memory.
Maintenance verification runs outside the operation's elapsed and allocation sample.

File workloads separate freshly reopened handles from warm handles.
Memory workloads separate newly constructed handles from warm handles.
A warm handle receives one complete unmeasured workload before sampling.
Each memory first-handle sample receives a separately generated fixture.
File reopen samples reuse the source file and reopen its database handle.
All states use identical logical parameters and checks.

Operating-system cache control is unavailable and recorded as `os_cache_control: unavailable`.
Reopening a file does not establish a cold filesystem cache.
The output makes no cold-cache timing claim.
The samples describe one run, without comparisons to other implementations or portable performance guarantees.

## Shared-history characterization

The benchmark also measures 25 shared histories in each profile.
One fixture shares a 128-element array.
Another retains a depth-600 array chain and a 64-element array in every history.
Fixture creation, conversion, and successful verification have separate timings.
Each record includes history length, source size, destination size, and their ratio.

Conversion has a ten-second diagnostic timeout for these fixtures.
A timeout records elapsed time through abort cleanup and the actual remaining destination size.
It has status `timeout`, no verification sample, and no successful conversion sample.
The cutoff bounds this diagnostic; it is not a performance pass threshold.
Conversion copies shared logical nodes separately, so retained histories can increase runtime and output size substantially.

## Observed run

An aarch64 Linux run used MRI 4.0.9 and `ruby:4.0.9-slim` on November 5, 2026.
The 768 MiB workload completed in both profiles under a 268,435,456-byte cgroup limit with zero swap.
The observed cgroup peak equaled that limit; OOM and OOM-kill event counts were zero.
Both offset caches peaked at 16,384 entries. Independent inspection directly observed disk spill for the Ruby profile.
Other validation jobs ran concurrently, and operating-system cache state was uncontrolled.
These measurements establish this workload's completion and output cost.

| Source profile | Source bytes | Fixture seconds | Conversion seconds | Conversion output bytes | Compaction seconds | Compaction output bytes |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Portable | 818,396,326 | 39.962 | 53.047 | 1,644,815,197 | 8.370 | 805,827,485 |
| Ruby | 833,361,937 | 130.068 | 32.251 | 1,633,809,495 | 8.866 | 807,393,651 |

Conversion preserved both histories and independently copied their shared payloads.
Compaction preserved one latest history.
Conversion verification took 6.030 and 4.601 seconds; compaction verification took 4.636 and 5.970 seconds, respectively.

The separate 1 MiB benchmark peaked at 197,292,032 cgroup bytes and recorded zero OOM events.
Its shared-history results were:

| Source profile | Depth | Fixture seconds | Source bytes | Conversion result | Destination bytes |
| --- | ---: | ---: | ---: | --- | ---: |
| Portable | 0 | 0.069 | 48,219 | Completed in 1.303 s | 1,560,437 |
| Ruby | 0 | 0.148 | 100,661 | Completed in 1.030 s | 941,187 |
| Portable | 600 | 0.328 | 220,945 | Timed out after 10.019 s including cleanup | 0 |
| Ruby | 600 | 1.391 | 648,584 | Timed out after 10.018 s including cleanup | 0 |

The shallow conversions expanded output to approximately 32.36 and 9.35 times source size.
The deep cases provide interrupted diagnostic results, not completed conversion timings.
